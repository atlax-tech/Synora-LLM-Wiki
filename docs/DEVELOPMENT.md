# Synora Wiki 开发规范

适用范围以 [PRODUCT §5.3](PRODUCT.md#53-当前服务与交付边界) 为准；DEFERRED 项不进入依赖、完成率或退出门槛。

## 实现原则

- 完成用户批准的功能范围，但实现始终选择当前阶段能成立的最小方案。
- 优先复用现有代码、标准库和 macOS 原生能力；不为未批准的未来需求搭脚手架。
- 修复共享根因并检查直接调用方；不借机重构无关代码。
- 只有改动实际触及数据格式、权限、安全、UI 或外部集成时，才补对应迁移、恢复、可访问性或故障测试。

长期架构不变：用户操作先成为本地原子事务；主线程只做 UI；Feature 不直接依赖 GRDB、供应商 SDK、WASI 或 Keychain；用户、AI 和导入写入统一经过 Command → ChangeSet → Transaction；原始内容不可被模型静默覆盖；派生层可重建。

## 完成与验证

一个普通改动完成只需：

1. 要求的行为已实现，不留下会误导用户的假入口。
2. 运行最接近改动的自动检查或可重复手工检查。
3. 不隐瞒已知回归、未验证项或环境阻塞。

额外证据按影响触发，不按提交次数触发：

| 影响 | 需要的补充验证 |
|---|---|
| 持久化格式/迁移 | 最小升级与恢复用例 |
| 用户可见 UI | 受影响界面的键盘/可访问性/视觉检查；完整矩阵在所属阶段或版本出口运行 |
| 外部集成、AI 或 Skill | 相关的成功、拒绝/失败和取消路径 |
| 密钥、权限或不可撤销数据 | 安全边界与恢复检查，不得因精简跳过 |

探针只回答预先写明的技术问题。mock、fixture 和小数据可用于重现与对比；探针不承担生产功能的完整性、全规模性能或发布验收。

## Git 与评审

- 首版发布前直接在 `main` 开发；首版发布后再配置保护分支。
- 一个完整、可回退的改动对应一次提交。提交前运行相关检查，不强制全量回归、独立角色、PR 模板或完整证据包。
- 完整版本/发布候选收口时，才运行全量回归和独立对抗审查；高风险改动或用户明确要求可单独提前。
- 阶段结束时统一推送 GitHub；其他推送需用户授权。

## 阶段与记录

- 阶段启动只检查直接依赖和当前所需的设备/配置；DEFERRED 项不阻塞。
- 阶段结束只运行该阶段的退出门槛。发布构建、空机恢复、全量性能/可访问性/安全矩阵属于完整版本出口，除非某阶段明确交付该能力。
- 只在决策、状态、公开合同或已知限制变化时更新 ADR、traceability 或开发日志；不随每次提交重复同步。
- Harness 只用于初始化、流程/权威文档变更、明显漂移或阶段/版本收口；普通代码提交不刷新 Harness 指纹。

治理检查只需：

```sh
git diff --check
git status --short --ignored
```

原生构建和测试命令见 [TESTING](TESTING.md)；未实际运行的检查不得报告为通过。
